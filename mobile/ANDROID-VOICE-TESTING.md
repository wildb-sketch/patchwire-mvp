# Android voice room reliability

## Bluetooth and headset routing

The later November 20 recording identifies Bluetooth as the failed output; the user confirmed a paired watch. Automatic Android 12+ HFP routing now checks the connected profile and device class, excludes identified wearables, and uses the loudspeaker while profile information is loading or no connected headset matches. AudioManager's port list alone no longer proves that earbuds are connected. Bluetooth addresses and class metadata stay local; display names are not used to identify watches.

Failed Bluetooth devices stay excluded for the current connection inventory. Stale communication-device callbacks, WebView startup and port-ID changes cannot re-enable a failed route; actual connected-profile changes or an explicit output choice can retry it. Speaker retries and unverified/system states retain the microphone's hardware generation, so output recovery cannot repeatedly destroy and recreate AudioRecord. An unconfirmed speaker deadline retains the speaker preference instead of clearing it back to Android's call earpiece. A late successful confirmation can settle that preference without replacing capture.

**Room options → Audio output** (also available from **Profile → Broadcast & Audio Hardware**) offers Automatic (headsets), Phone loudspeaker, and Bluetooth audio. The choice is saved natively. Phone loudspeaker ignores paired watches and other Bluetooth devices until the user selects Automatic or Bluetooth again. Explicit Bluetooth can include a wearable if the user chooses it. This also covers devices whose manufacturer does not identify their watch class correctly. Output selection neither starts a room service outside a room nor opens a listener microphone; it preserves a speaker's mute intent. Changing a pinned microphone back to the selected communication route is an explicit user action. No additional Android permission is introduced.

Validation must include a watch paired by itself, watch plus earbuds, removing earbuds while the watch remains paired, repeated stale callbacks after failed Bluetooth, saved phone-speaker choice across rooms, Nearby devices denial/grant, and leaving during an asynchronous profile bind. Confirm real loudspeaker playback and phone microphone transmission with another participant. Do not confuse the separate Mute sound button with output selection. Browser and native tests exercise policy and lifecycle; actual Android audio drivers and watch metadata require a device check.

The room service now owns communication routing as well as audio focus. It enters `MODE_IN_COMMUNICATION`, follows audio-device additions/removals and uses `setCommunicationDevice` on Android 12+ to select a wired/USB headset, a Bluetooth HFP/LE headset, or the phone speaker. Android selects the matching input for that communication output. Android 5.1–11 uses the legacy SCO connection and waits for its connected broadcast. Leaving releases the route, SCO request, callbacks and communication mode.

Android 12+ requests **Nearby devices** (`BLUETOOTH_CONNECT`) for paired headset access before capture/room startup; older Android uses the normal `BLUETOOTH` permission capped at API 30. No Bluetooth discovery, scan or location permission is added. Denial leaves the phone microphone and playback usable. Grant Nearby devices in Android Settings if previously denied. The implementation follows [Android's self-managed audio routing guide](https://developer.android.com/develop/connectivity/bluetooth/ble-audio/audio-manager) and [Bluetooth permission guidance](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions).

Native route readiness is asynchronous: a successful output request alone does not prove the Bluetooth microphone is recording. Capture starts using the current system route while a communication-device request is pending, because some devices defer that request until recording/playback is active. A pending snapshot has generation zero. Confirmation then replaces provisional capture, including when the event arrives during getUserMedia. On Android 12+, phone/wired requests have a two-second deadline and Bluetooth has five seconds before phone fallback; the fallback has a two-second deadline. Legacy SCO retains its platform-specific 30-second connection window. Older APK bridge waits are bounded to 800 ms in the web client. Device failures produce a local notice, not a room-wide connection error.

The November 20 recording shows a headset-error toast shortly before the reported switch to loudspeaker. The previous pending-route logic ignored mismatching output callbacks and never reasserted an accepted request until its 30-second fallback. WebView startup can overwrite that initial request. Pending phone/wired requests now clear and reapply a mismatching preference at 250 ms intervals, capped at four requests per attempt without extending the deadline. Reasserting the same route does not create a new microphone generation. Bluetooth handshakes are not repeatedly restarted. Recovering the requested loudspeaker is success and emits no headset warning. Actual route failures include their source; older APK events without that context use a generic output error. The hardware panel distinguishes the phone call earpiece from the loudspeaker.

The clients also request a native output refresh immediately after microphone acquisition and after remote audio starts playback. This restores preferences after WebView starts its actual AudioRecord/AudioTrack, including listener-only playback, without waiting for an output callback or blocking room controls. Browser coverage verifies that receiving playback refreshes the native route while the listener microphone remains closed.

Native tests reproduce Android accepting the first speaker preference while continuing to use the call earpiece until that stale preference is cleared. They verify recovery at 250 ms, stable microphone generation, bounded unavailable-output handling, real Bluetooth failure context, Leave cancellation and telephone-call protection. On the affected phone, join with earbuds disconnected and another participant speaking: loudspeaker playback should start promptly without the delayed toast. Repeat stage acceptance, earbuds connect/disconnect and manually muted capture. Automated tests do not establish actual device playback latency.

Both web designs replace their microphone on a confirmed native route change, retaining the existing WebRTC peers/senders and the current user mute state. Old tracks are stopped with their handlers detached; late captures are discarded after another device change, demotion or Leave. Hardware-ended Android tracks have a short device-change debounce and bounded recovery, with one retry for transient capture-busy errors. Permission refusals still require explicit Unmute. Stale saved device IDs reset on a new native route; **Broadcast & Audio Hardware → Automatic (phone / headset)** also clears an override. Older APKs continue using the existing phone-capture path until upgraded.

Automated checks cover Android 9 legacy SCO and Android 12/14 communication-device routing, preconnected HFP/LE headsets, hot-plug/unplug, wired/USB priority, denied permissions, delayed confirmation, capture-before-route confirmation, timeouts and cleanup. Android 12 tests reject legacy SCO startup when the modern communication-device API owns routing. Separate recording-device checks distinguish a selected Bluetooth output from an active phone microphone and leave unavailable input data unverified. Real Chromium peers additionally exchange fresh RTP after bootstrap and simulated native route changes while retaining the same peer and sender. These checks do not emulate a Bluetooth radio, earbud firmware or an Android audio driver.

On two real phones, with the second person confirming actual received speech:

1. Connect earbuds before opening Whassabi. Join/speak, allow Nearby devices and verify received audio plus the earbud microphone.
2. While speaking in a room, connect earbuds, disconnect them, and reconnect. Both directions should switch without restarting the app or leaving the room.
3. Repeat while manually muted and while using another app/locking the screen. Headset changes must preserve mute; Unmute must restore speech.
4. Repeat with wired/USB headphones if available. Leave and verify other apps resume their normal audio route. Record phone, Android/WebView and earbud models if a step fails.

## Diagnosis

The tracked Android project is a source overlay: `prepare-android` generates the actual manifest and Gradle project (the generated `mobile/android/` is ignored). Both `public/index.html` and `public/neon.html` are remotely served web clients; `mobile/www/index.html` is only the server launcher. Capacitor loads the Worker URL from `capacitor.config.json`.

The frontend called `window.RoomPlugin`, which is not the registered Capacitor plugin API. Errors were swallowed, so no foreground service or notification started. The service itself had no wake lock, notification permission request, or callback to the WebRTC client. Its Mute changed only notification state, and Leave stopped only the service. It was sticky even though it cannot restore a WebView's peer connections after process death. Mic capture also raced on repeated room updates; errors were all mislabeled as browser permission failures. Every WebSocket close stopped microphone tracks and the service immediately.

The standalone registered `RoomPlugin` now uses Capacitor's injected `nativePromise` / `addListener` API, including on remote pages. Room start waits for native confirmation that `startForeground` succeeded. Listeners use `mediaPlayback`; microphone mode requires `RECORD_AUDIO` and a visible activity when first enabled, as required by Android 14. Accepting a stage invite or requesting to speak prepares microphone eligibility while visible. Notification permission on Android 13+ is separate; denied or disabled notifications are reported without blocking voice. CPU and Wi-Fi locks are held only for the active service lifetime. Capacitor 6 defaults to keeping the WebView running; its existing WebChromeClient handles origin-level capture after the runtime permission is granted. No replacement WebChromeClient or blanket permission grant is installed.

Capture is serialized, stale capture results are stopped, and permission failure leaves the speaker muted with an explicit Unmute retry. Both designs keep their current UI. Notification mute changes the actual track, signaling state, and notification; listener notifications omit microphone controls. Notification Leave immediately leaves: the server atomically hands a host room to the first current co-host, or ends the room if none exists. This also works when the membership changed during a disconnect. The in-app host handover confirmation remains unchanged. Brief signaling disconnects preserve audio and mute state; reconnect resynchronizes membership and peers. A heartbeat detects stale signaling connections. Process death, task dismissal, page navigation, or a real room exit releases the service; a killed transport is never represented as an active call.

## Install and deploy together

This fix spans the APK **and remotely hosted frontend / signaling code**. Installing only a new APK against the old deployed pages will still run the old broken JavaScript. Deploy this branch's `public/` and `cloudflare/src/worker.js` to the test Worker, then install the APK from the same revision. A refreshed page is required; the existing service worker is network-first. Production deployment is not part of this change.

The debug signing key should match the installed app when updating. Otherwise uninstall first (which also resets Android permissions). A self-hosted Node deployment uses the updated `server.js`.

Initial capture is allowed while native output routing settles. Connection failure has a bounded fallback and leaving releases routing.

A headset-profile disconnect excludes a stale classic Bluetooth entry until a new connection signal, so unplugging does not immediately reselect the removed headset. Automatic phone output selects the loudspeaker rather than the call earpiece. Android 12+ mode changes are observed to restore communication mode after WebView resets it; an active telephone call is not overridden. Permission errors remain errors rather than being hidden by fallback. ## Swipe-away cleanup

The recording exposed two separate issues: each remaining peer locally raised a generic network/TURN error when the dismissed participant's audio link failed, and the native service tried to leave through a JavaScript listener in a WebView that Android could already be destroying.

Task dismissal and a finishing Activity ask the existing service to send an authenticated HTTPS leave request directly. It waits at most seven seconds before stopping, holds credentials only in memory, does not follow redirects, and only accepts the current WebView's HTTPS origin. System/configuration destruction instead stops the service and uses server disconnect grace, preserving the opportunity to recover a seat. Normal Home/app switching and screen locking do not invoke this dismissal path. Every room join/reconnect issues a private leave token; the server rejects stale leases so a delayed old request cannot remove a rapidly reopened session. Explicit in-app Leave still follows the existing host confirmation flow. Both backends have equivalent cleanup endpoints and cancel the departed seat's grace timer.

If Android force-kills the process without any lifecycle callback, or the phone is offline, immediate network cleanup cannot be guaranteed: the normal 45-second disconnect grace remains the fallback. Other participants now see one message naming whose audio disconnected and saying it is waiting for reconnection, rather than suggesting their own network needs TURN. Removed peer connections cannot emit late warnings.

Repeat the original recording test: while another device watches the room, swipe the Android task away, verify prompt membership removal without the TURN warning, then rapidly reopen and confirm an old leave request cannot eject the new session. Recheck 10-minute locked-screen audio to ensure ordinary background operation is unchanged.

## Audio recovery during Wi-Fi/mobile handover

Chat uses the signaling WebSocket; voice uses independent WebRTC ICE transports. A healthy chat connection does not prove that the media path survived a network change. Previously, failed media only produced a toast, and a renegotiation offer destroyed the existing peer/sender. ICE configuration could also arrive after initial room offers had already started.

Both designs now share `public/room-audio.js`. It serializes SDP changes, uses polite/impolite collision handling, associates answers with their current offer, buffers early ICE candidates, ignores stale ICE generations, and retains the microphone/transceiver during renegotiation. Failed/disconnected media and unanswered initial offers trigger bounded ICE restarts with refreshed server configuration; signaling outages wait for the socket before consuming retries. A clickable retry toast and return-to-foreground recovery are available after exhaustion. Successful recovery clears watchdogs even on browsers that keep the connection state connected throughout a restart.

The Android plugin observes default-network changes without requesting additional dangerous permissions. Both native events and browser online/connection events replace a stale signaling socket and restart media. Resuming a room preserves peers and microphone/mute state. Initial ICE settings are loaded before opening signaling. Lock-screen foreground-service behavior and native dismissal cleanup are unchanged.

`npm test` runs 55 unit/integration checks. `npx playwright install --with-deps chromium && npm run test:webrtc` runs five real Chromium tests: packet flow after simultaneous ICE restarts, preserving mute, signaling outage recovery, peer reopening, and both complete app designs recovering while retaining microphone identity, room, chat, and mute. GitHub Actions runs both suites before APK assembly/lint. These tests exercise real WebRTC but cannot emulate a particular mobile carrier or Android OEM.

Repeat Wi-Fi → mobile → Wi-Fi handover with another participant checking actual received speech; repeat while locked and muted. Verify recovery without leaving the room, no accidental unmute, and chat continuing. A short interruption during handover is expected; permanent silent audio is not. Also repeat initial connection several times on each network and the 10-minute lock-screen/swipe-away checks.

`/healthz` includes a non-secret `X-Voice-Relay` header: `configured` means the server has a TURN URL, and `missing` means only STUN/direct paths are available. It does not prove that relay credentials work. ICE restart cannot make blocked peer-to-peer carrier paths work without a reachable TURN relay. Existing server settings remain `TURN_URL`, `TURN_USER`, and `TURN_PASS`; do not paste credentials into chat or commit them. Check the deployed header before claiming mobile-network coverage is complete.

Simultaneous connection/restart requests elect one offer owner by participant ID. The other endpoint requests negotiation instead of rolling back a fresh ICE gatherer, which can stall candidate generation in Chromium. Legacy offer collisions retain the polite/impolite fallback. The live relay check on November 17 confirmed `X-Voice-Relay: missing`; relay provisioning is still required for carrier paths that block direct audio.

## Switching to other Android apps

The service previously sent a permanent microphone Mute command on both transient and permanent audio-focus loss. A media app taking playback focus could therefore change the room's user mute setting without a notification action. Focus changes now log under `WhassabiRoom` and leave microphone intent unchanged; Android still controls capture priority when another app uses the microphone.

While a room service is active, Activity pause/stop explicitly retains WebView renderer importance and resumes WebView processing. Capacitor already defaults to keeping its WebView running, so these calls are defensive and do not prove continuous capture on an OEM device. The room's media transport still lives in the WebView. System destruction no longer sends a deliberate Leave unless the Activity is actually finishing, and transport cleanup preserves an already-running swipe-away leave request.

Both clients use `room-heartbeat.js`. After a delayed background timer, it sends a fresh liveness probe instead of closing a socket merely because the last pong is old. Any current socket traffic confirms liveness; an unanswered socket still reconnects after an uninterrupted timeout. This addresses false client disconnects, not process death or blocked ICE transport. Five fake-clock regression tests cover scheduler suspension, live traffic, genuine timeouts, stale sockets, and intentional shutdown.

Retest with a second participant listening to actual speech for at least two minutes in each case: another app showing a static page; an app playing audio; and a phone call or recording app. For the first two, verify continuous transmission, no automatic mute, no membership loss, and a visible room notification. For competing microphone use, record any Android-imposed capture interruption and verify recovery when it ends. Repeat with a manually muted room and confirm it stays muted. Then repeat locked-screen audio, notification Mute/Unmute/Leave, network switching, and swipe-away cleanup. Capture the phone model, Android/System WebView versions, triggering app, and `adb logcat -s WhassabiRoom` if anything fails. Browser tests cannot validate these hardware behaviors.
